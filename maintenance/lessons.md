# 维护经验

- 固定来源版本和归档哈希，才能让目录条目在后续运行中可复核；不要只保存指向默认分支的链接。
- 许可必须按实际源文件所在目录解析。保留原仓库版权、许可证和适用的 `NOTICE`；根目录 MIT 不改变第三方原作的许可。
- 逐字引用应能在对应固定版本的 `SKILL.md` 中找到。模型生成的双语摘要需要独立审核和确定性校验，模型通过不能证明技能可执行。
- 数据缺失不能写成没有重大消息。首次晨报条目的此项缺陷已交回 GLM-5.3-flash 重做，并将区别加入生成与独立审核规则；数据源不可达时明确保留数据缺口。
- 分清两个状态：`sourceVerified` 表示已核对来源与许可；`executionVerified` 表示实际运行经过记录。当前条目不因入目录而成为已实测技能。
- 对发现的新仓库采用有界审查：每轮最多新增 3 条；现有来源变化超过 6 条时暂停该轮，转人工查看变化范围。
- 候选总复核次数有上限；记录已拒绝内容的哈希，避免来源未变时每天重复送审。已收录仓库仍需每日跟踪。
- 若已收录仓库根许可证变化，停止发布并转人工审阅，不能假设新许可自动沿用。
- 先在暂存目录生成并校验所有变更。任何必需源、许可证、模式或浏览器检查失败，保留线上上一版并上传失败收据供诊断。
- 成功的 no-change 运行仍需留收据；它证明本轮校验链走完，即使目录内容相同。
- 主站和旧站都应读取 GitHub 的同一份 canonical catalog。维护发布后要核对仓库目录与页面读取结果，不把一次 CI 成功等同于用户侧 readback。
- GitHub 原始文件的 CDN 可能在提交后短暂返回旧内容。镜像请求按分钟使用版本参数避开旧缓存；来源不可达时仍显示带日期的随站副本，浏览器检查分别覆盖这两个分支。
- 第三方技能只能按原仓库说明由使用者评估和安装；目录收录不自动授权运行、交易或上传到其他平台。
- schedule、secrets、workflow 权限和收录边界属于维护者控制面。新自动化不能通过自动改写这些文件扩展自身权限。
